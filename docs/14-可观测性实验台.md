# 14 · 购物页面与可观测性实验台

> 一个**购物页面**：浏览商品、加购物车、下单；熔断、限流、链路追踪在背后自然发生。
> 底部有轻量的「系统状态」条，想深究时点开即可看到控制台入口。
> 技术栈：React 19 + Vite 8 + TypeScript 7 + pnpm + Tailwind CSS 4 + **shadcn/ui（Radix）+ lucide-react 图标 + sonner toast**。

---

## 1. 为什么需要它

熔断和链路追踪都是**运行时行为**——光看代码和 yml 配置很难建立直觉：

- 「失败率超过 50% 会熔断」——实际要发几个请求才跳？跳了之后什么样？
- 「限流 20 QPS」——并发多少才会被拒？被拒的响应长什么样？
- 「一个 traceId 串起四个服务」——在 UI 上到底怎么展示？

实验台把这些变成**可点、可看、可反复试**的东西。

---

## 2. 访问

```bash
# 启动全栈后（注意：先构建 jar）
mvn -q -DskipTests package
docker compose up -d --build

# 浏览器打开
http://localhost:3000
```

页面布局：

| 区域 | 作用 |
|------|------|
| 商品列表 | 两件商品，显示价格与实时库存 |
| 购物车 | 加购、改数量、结算；下单成功后自动清空并刷新库存 |
| 底部系统状态条 | 熔断状态（读 Sentinel 真实状态）+ 成功/降级/限流计数 + 最近链路 |
| 「这是什么？」 | 点开后解释微服务架构，并提供 Sentinel / Zipkin / Nacos 控制台链接 |
| 店主演示（右上角，默认收起） | 故障开关：正常 / 报错 / 慢响应 |

---

## 3. 怎么玩

**正常购物**：选商品 → 加购物车 → 去结算。每一次下单都在真实走
`网关 → 订单服务 → 用户/商品服务 → MySQL`，底部计数会涨。

**想看熔断**（店主演示）：

1. 点右上角「🔧 店主演示」，切到「**报错**」；
2. 连续下几单，底部状态会变成「熔断中」，订单会收到友好失败提示；
3. 切回「正常」，**等 10 秒**，再**单独下一单**作为探测 —— 状态恢复「正常」。

> ⚠️ 熔断恢复三要素：**关故障 + 商品有库存 + 单次探测请求**。
> 如果商品库存被扣光（409）或还在报错，探测会一直失败，熔断就一直 OPEN。

**想看链路**：点底部「这是什么？」里的 Zipkin 链接，能看到一次下单跨四个服务的完整链路。

---

## 4. 后端支撑

实验台需要后端额外暴露两个能力：

| 端点 | 服务 | 说明 |
|------|------|------|
| `GET /lab/status` | order-service | 用反射读 `DegradeRuleManager.getCircuitBreakers()` 的真实状态 + 请求统计 |
| `POST /admin/fault?mode=OFF\|ERROR\|SLOW` | product-service | 故障注入开关，Controller 层在扣库存前注入异常/延迟 |

> 这两个端点**仅用于学习演示**，生产环境不要暴露（无鉴权）。Sentinel 状态读取用反射是因为
> `getCircuitBreakers()` 在 1.8.9 是包级私有；生产应改用 Micrometer 指标。

## 6. 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 页面显示「连接异常」 | order-service 未启动 | 检查 `docker compose ps` |
| 熔断状态一直是 UNKNOWN | 规则未加载 / 反射失败 | 看 order-service 日志，确认 SentinelRuleConfig 生效 |
| Zipkin 瀑布图无数据 | 采样率或 endpoint 错 | 见 [08-链路追踪](./08-链路追踪-Micrometer-Zipkin.md) |
| 故障注入没效果 | 模式没切过去 | `curl http://localhost:8082/admin/fault` 查看当前模式 |
| 前端容器构建慢 | 首次拉 node/nginx 镜像 | 后续构建有缓存，会快很多 |
